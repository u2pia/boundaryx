## 〔C·改〕1. 产品摘要

AI Native SDLC Control Plane 是一个核心完全开源、可自托管、Agent 中立的研发控制层，面向 **3–8 人的研发团队**，管理 AI 参与的软件变更从需求意图到生产反馈的全周期追溯链。

第一阶段要解决的问题是**审查带宽**：让团队里任何一个人都能快速、安全地接受另一个人的 Agent 产出的变更。

首个产品闭环：

```text
关联 Issue 形成 Intent（含验收标准）
→ 编译 Agent Context
→ 在隔离 Workspace 执行 Agent
→ 运行 Evaluation 并映射到验收标准
→ 生成 Evidence 并渲染到 Pull Request
→ 由非作者审查与批准
→ 合并
→ 生产反馈回流为新的评估项或新的 Intent
```

〔C·改〕相比 v0.1，闭环有三处实质变化：起点从"创建 Intent"改为"关联既有 Issue"；终点从"创建 PR"延伸到"合并 + 反馈回流"；审批明确为**非作者**执行。

## 2. 产品目标

### 〔C·新〕G0：降低单次变更的审查成本

把审查一次 AI 变更所需的人工投入显著降低，并让审查负载在团队内可见。这是第一阶段唯一的必达目标；G1–G6 是它的手段。

### G1：规范需求意图

让团队用结构化方式补齐目标、范围、约束、验收标准和风险，**附着在既有 Issue 上**，而不是把模糊 Prompt 直接交给 Agent，也不是另建一套需求系统。

### G2：提供可复现上下文

记录 Agent 实际使用的文件、规则、知识和版本，使一次执行可以向他人解释并原样重放。

### G3：提供受控执行

通过 Workspace、命令、目录、网络、凭证、时间和费用预算约束 Agent 行为，并**如实区分哪些约束是预防性的、哪些只是检测性的**。

### G4：建立评估门禁

把编译、测试、安全、业务场景和策略检查组织为统一 Evaluation Contract，并建立验收标准与评估项的映射。〔C·新〕其中必须标注哪些评估是本次运行新造的。

### G5：形成可被快速阅读的证据

为每次运行生成可携带、可关联 Pull Request 的 Evidence，**以审查者能在几分钟内读完为设计目标**，而不是以完整性为设计目标。

### 〔C·改〕G6：分级自治

第一阶段默认 AI 执行、人审查合并（L3）。低风险且证据充分的变更在月 5 起开放自动合并试验，目的是把人的注意力集中到高风险变更上。**不采用"全部变更必须人审"的策略**，理由见 [VISION.md](VISION.md) §6.9。

### 〔C·新〕G7：团队级可见度

让团队推动者能看到审查负载分布、返工率、首次评估通过率与证据展开率，用于调整分级策略。

## 〔C·改〕3. 非目标

v0.1.0 不建设：

- Web 管理与审批后台（**审查界面就是 GitHub PR**）；
- 多租户、RBAC 与企业身份联邦；
- Issue Tracker 替代品；
- 多仓库与跨仓库变更；
- 通用多 Agent 编排器；
- 自研 Coding Agent；
- 自研向量数据库；
- GitLab、Jira 与 ServiceNow 集成；
- 自动生产发布；
- Agent Marketplace；
- 企业级组织与计费系统；
- 完整知识图谱；
- 证据签名与合规报表。

〔C·改〕相比 v0.1，新增前四项为非目标；"大型 Web 管理后台"收紧为"任何 Web 审批后台"。

## 〔C·改〕4. 目标用户

### 4.1 团队画像

| 参数 | 约束 |
| --- | --- |
| 规模 | 3–8 人，1 名推动者 |
| 平台工程 | 无专职平台工程师 |
| 仓库 | 1 个主仓库 |
| 合规 | 无强制审计要求 |
| 现有工具 | GitHub + 某个 CI + 某个 Issue Tracker |
| 运维能力 | 能运行一个 `docker compose`，不愿维护数据库集群 |

### 4.2 双 Persona

**Persona A：变更作者**

- 使用一个或多个 Coding Agent 完成真实任务；
- 需要保留对代码、权限和合并决策的控制；
- 希望减少"提交后被打回重做"的返工。

**Persona B：变更审查者（第一阶段更重要）**

- 需要审查同事用 Agent 产出的变更，而自己同时也在写代码；
- 无法逐行阅读每天多份大体积变更；
- 最怕两件事：漏审引入故障，以及为了不堵塞而闭眼通过。

### 4.3 核心 Job to Be Done

作者：

> 当我把一个真实开发任务交给 AI 时，我希望它在明确要求和受限权限下完成工作，并自动产出足以让同事放心接受的材料，让我不用再手写一遍说明。

审查者：

> 当同事把一份 AI 产出的变更交给我时，我希望在几分钟内看清它要解决什么、依据什么上下文、哪条验收标准被什么证明了、哪些证明是它自己新造的，从而安全地决定接受或退回。

### 4.4 后续 Persona

- 多团队的平台工程师；
- 研发效能负责人；
- AI 治理与安全负责人（有合规要求的组织，第二阶段）。

## 〔C·改〕5. MVP 用户旅程

旅程分两段。**阶段 0 必须在只有一个人安装时就完整可用**，否则团队采用无法启动。

### 5.1 阶段 0：单人安装，零团队决策

```bash
ainative init          # 生成 .ainative/，识别现有 CI 与 Issue Tracker
ainative link 123      # 把 GitHub Issue #123 提升为 Intent，补齐验收标准
ainative run INT-0001  # 隔离执行 Agent
ainative pr create     # 创建 PR，并把证据渲染为 PR 评论 + Check
```

产出目录：

```text
.ainative/
├── project.yaml
├── intents/
├── specifications/
├── policies/
├── evaluations/
├── agents/
└── evidence/
```

此阶段的可见价值全部落在 PR 上，团队其他人不需要安装任何东西就能受益。

### 〔C·新〕5.2 阶段 1：团队生效

```bash
ainative serve                    # 单节点共享服务，GitHub OAuth 登录
ainative review queue             # 待审队列与负载分布
ainative approve RUN-0001 --as @bob
ainative request-changes RUN-0001 --reason ...
ainative metrics --since 30d
```

新增的是**第二个人**这条路径，v0.1 完全缺失：

```text
Run 完成 → 证据渲染到 PR → 按负载与风险分配审查者 → 通知
→ 审查者展开证据 → 批准 / 退回（带理由）
→ 退回则产生新 Attempt，返工原因记入 Feedback
→ 合并 → 生产信号回流
```

### 5.3 关键环节说明

**关联意图**：Intent 以 Issue 为权威来源，只补 Tracker 装不下的三样东西——验收标准、约束、风险等级。Issue 的标题、状态、讨论和分配始终以 Tracker 为准，冲突规则见 [DOMAIN_MODEL.md](DOMAIN_MODEL.md)。

**编译上下文**：输出可编辑的 Context Manifest，列出文件、规则、来源、原因、敏感性和估算规模。〔C·新〕同时记录 Agent 实际读取的文件，与 Manifest 并列呈现差异——Manifest 是声明，实际读取是事实，两者不一致本身就是审查信息。

**执行 Agent**：创建独立 Git worktree，并在**强制容器**内执行；策略在容器与文件系统边界上强制。〔C·改〕v0.1 把容器列为可选增强，导致目录禁改这类成功标准无法真正实现，现改为强制。

**执行评估**：至少支持命令退出状态、JUnit、SARIF、Coverage、自定义 JSON Assertion 与验收标准映射。〔C·新〕对每个评估项标注来源：既有 / 本次新增 / 本次被修改。任何"本次新增的测试"不得作为某条关键验收标准的唯一证据。

**审查与批准**：批准者必须是具名的外部身份（GitHub 账号），默认不能是作者本人。产品记录批准前是否展开过证据。

**创建 PR**：PR 包含 Evidence Summary，并通过 GitHub Check 显示门禁状态。

## 〔C·改〕6. MVP 功能范围

| 能力 | v0.1 范围 |
| --- | --- |
| Intent | 由 GitHub Issue 提升；补验收标准、约束、风险；版本化；双向同步 |
| Specification | 内置最小格式 + 外部 SDD 工具导入 |
| Context | 显式清单 + **实际读取对账** |
| Agent | 一个真实 Agent 的深度集成 + Mock Adapter；Adapter Contract 在接第二个 Agent 时才定型 |
| Workspace | Git worktree + **强制容器** |
| Policy | YAML 目录、命令、网络、预算与审批规则；每条标注预防/检测 |
| Evaluation | 命令、JUnit、SARIF、Coverage、JSON；AC 映射；**新增证明标注** |
| Evidence | 开放 Schema + **PR 评论渲染**（主要交付形态） |
| Review | 待审队列、审查者分配、负载可见、退回与返工链 |
| Approval | 基于 GitHub 身份的具名审批；默认禁止自批；证据展开记录 |
| Team Service | 单节点共享服务、SQLite、事件日志、并发冲突检测 |
| GitHub | Issue 同步、PR 创建、Check 状态、评论渲染、OAuth |
| Notification | 一个通道（GitHub 通知或 Slack Webhook） |
| Metrics | 审查人时、证据展开率、首次通过率、返工率 |
| Release/Feedback | 最小形态：合并与生产信号回流为新评估项或新 Intent |
| Observability | 结构化事件 + 可选 OpenTelemetry Exporter |

〔C·改〕相比 v0.1 新增 Review、Team Service、Notification、Metrics、Release/Feedback 五行；Workspace 的容器从可选改为强制；Agent 从"一个参考集成 + 通用 Adapter"改为"一个深度集成，Adapter 延后定型"。

## 7. 非功能要求

### 〔C·改〕7.1 Self-hosted First

核心流程不依赖外部 SaaS，联网能力必须可关闭。团队共享服务运行在团队自己的机器上。〔C·改〕v0.1 的 "Local First" 被误读为单机架构，与团队定位不兼容。

### 〔C·新〕7.2 单命令部署，零迁移升级

目标团队没有专职平台工程师。部署必须是单个二进制或单个 `docker compose up`；升级不得要求手工数据迁移。**不引入需要独立运维的基础设施**（外部数据库集群、消息队列、Kubernetes）。第一阶段状态存储为 SQLite + 文件 + Git。

### 〔C·新〕7.3 多用户并发

同一仓库可能同时存在多个 Run。系统必须检测并处理：目标文件重叠、分支冲突、Intent 之间的规格矛盾、同一资源的竞争。并发语义属于领域模型，不是实现细节。

### 〔C·新〕7.4 身份不可自证

审批、审查分配和责任归属使用外部身份源（第一阶段为 GitHub）。不接受本地配置文件中的身份字符串作为审批凭据。

### 7.5 Agent Neutral（有限）

核心状态机不包含特定 Agent 的专有字段。〔C·改〕但第一阶段**公开承认是 agent-specific 的**：只深度集成一个具备可用拦截机制（hook / 权限模式 / MCP）的 Agent。Adapter Contract 在接入第二个 Agent 时定型，而不是在接入第一个之前凭想象定义。为了中立性放弃唯一可行的强制手段，是把原则排在功能之前。

### 7.6 Model Neutral

规格生成、评估和 Agent 执行允许使用不同模型，也允许完全不使用远程模型。

### 7.7 Deterministic Core

状态转换、策略门禁、证据打包、ID 生成和审批判断必须由确定性程序执行，不交给模型自行决定。

### 〔C·新〕7.8 强制边界

任何声称"策略强制"的运行必须在容器边界内执行。不在可强制边界上的规则必须在证据中标注为检测性，不得呈现为已阻止。

### 7.9 Private by Default

源代码、上下文和完整 Trace 默认留在团队内部。外发内容必须显式配置并可审计。〔C·改〕本地敏感 Trace 的保留与脱敏策略从"发布前决定"提前为**月 1 与威胁模型一起产出**，因为它是本条 NFR 的实现前提。

### 7.10 Recoverable

运行必须支持取消、失败恢复和保留 Workspace。不得因 CLI 或服务重启而丢失关键状态。

### 7.11 Portable Evidence

Evidence 使用开放格式，不要求依赖本项目 UI 才能读取。Schema 自第一版起带 `schema_version` 与迁移说明。

## 〔C·改〕8. 成功标准

### 8.1 六个月价值标准（可证伪，任一不达标即转向）

1. **审查人时**：使用后每个被接受变更的审查投入相对基线下降 ≥ 30%（基线必须在月 1 先测）。
2. **证据展开率**：非作者审批者点批准前展开过证据的比例 ≥ 70%。**低于 50% 判定为产品在生产橡皮章审批，核心假设不成立。**
3. **自然扩散**：至少一个试点团队中，除推动者外有 ≥ 2 人在无人催促的情况下主动使用。

〔C·新〕v0.1 的成功标准全部是能力检查，缺少价值检查与停止条件，这是原方案最大的方法论缺口。

### 8.2 六个月能力标准

1. 外部团队可在 30 分钟内完成安装与共享服务部署；
2. 至少支持一个真实 Coding Agent 和一个 Mock Agent；
3. 在真实 GitHub 仓库完成一次 Issue → 合并的端到端流程，且审批者非作者；
4. 未通过关键验收标准的变更无法进入批准状态；
5. 每次运行都能生成完整、机器可读的证据，并渲染到 PR；
6. 在容器边界上可证明 Agent 无法修改策略禁止的目录（含 `.ainative/policies/` 自身）；
7. 离线模式可完成除 GitHub 同步外的全部核心流程；
8. 至少一名外部使用者可在无作者协助下完成示例流程。

### 8.3 不采用的成功指标

AI 生成代码比例、Prompt 数量、Agent 调用次数、代码行数、GitHub Star 数量、未说明质量前提的开发速度提升。

## 〔C·改〕9. 六个月路线图

重排的核心原则：**用户可见的输出在月 1，审批门禁排在能看见审查负载之后。** 没有负载数据无法设计分级，而不分级的全量人审必然橡皮章化。

### 月 1：可见价值 + 基线

- PR 评论形态的 Evidence 渲染；
- 验收标准 ↔ 评估项映射；
- **本次新增测试的标注**；
- 审查人时基线测量；
- 威胁模型（含 prompt injection、`.ainative/` 自我提权）与敏感 Trace 策略；
- Intent / Run / Evaluation / Evidence Schema 初版 + 架构决策记录。

### 月 2：上下文与重放

- Context Manifest；
- Agent 实际读取对账；
- 运行重放；
- Git worktree 隔离。

### 月 3：团队生效

- 单节点共享服务（SQLite + 事件日志）；
- GitHub OAuth 身份；
- Run 队列与并发冲突检测；
- 待审队列、审查者分配、通知；
- 退回与返工链。

### 月 4：策略与强制

- 强制容器沙箱；
- YAML Policy 与稳定的 Decision Contract；
- 预防性 / 检测性标注；
- 命令、目录、网络、时间与费用限制；
- 人工覆盖及理由记录；
- 门禁状态机。

### 月 5：分级自治

- 风险评估与自治等级计算；
- 低风险自动合并试验（L4）；
- 审查负载与证据展开率指标；
- 首次评估通过率与返工率。

### 月 6：闭环与发布

- 合并后到生产的反馈回流（最小形态）；
- 生产信号转化为新评估项或新 Intent；
- 安装、升级、示例项目；
- 架构、威胁模型、贡献与 Adapter 文档；
- v0.1.0 发布。

〔C·改〕相比 v0.1：对象模型不再独占月 1；GitHub 工作流从月 5 提前到月 1（它是唯一的价值可见通道）；Team Server 从 6–12 个月提前到月 3；发布/反馈从 12–24 个月提前到月 6 的最小形态——小团队自己运维生产，是唯一能在六个月内闭合这条环的规模。

## 〔C·改〕10. 12-24 个月方向

以下是**方向，不是承诺**；是否进入取决于第一阶段的三条价值标准是否达成。

### 6-12 个月

- 多团队与多仓库；
- 共享策略与评估资产库；
- 第二个 Agent Adapter 与 Adapter Contract 定型；
- GitLab 与 Jira Adapter；
- OPA/Rego Adapter；
- Evidence 签名（Sigstore）；
- OpenTelemetry 语义扩展；
- 自动合并策略的扩大。

### 12-24 个月

- 企业身份与短期凭证；
- Durable Workflow Runtime（Temporal 评估）；
- 组织级 Intent / Evidence Graph；
- 受限自动发布；
- 合规导出与审计报表；
- 插件与 Adapter 生态；
- 商标与兼容性认证。

## 11. 开源策略

- 核心、Schema、CLI、Adapter SDK 和治理能力全部开源；
- 优先评估 Apache-2.0；
- 采用公开 RFC 和 Architecture Decision Record；
- 发布公开 Roadmap 和兼容性承诺；
- 不以隐藏核心治理能力的 Open Core 作为第一阶段策略。

许可证在发布首个代码版本前正式决定，并完成所有引入依赖的许可证审计。

〔C·改〕"商标和兼容性认证独立于代码许可证管理"移至 12-24 个月：在没有采用者之前建立认证体系没有对象。

## 〔C·改〕12. 主要风险

| 风险 | 影响 | 缓解策略 |
| --- | --- | --- |
| 〔C·新〕审批退化为橡皮章 | 证据形式完备、实质无效，制造虚假安全感 | 证据展开率作为否证指标；按风险分级；低风险自动合并以集中注意力 |
| 〔C·新〕两个权威数据源 | Intent 与 Issue 不一致，追溯链失真，第三周即成垃圾数据 | Issue 为权威源；Intent 只附着三类字段；同步冲突规则写入领域模型 |
