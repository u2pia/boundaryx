# AI Native SDLC Control Plane 愿景

> 状态：Draft v0.2（小团队 · 全周期）
> 日期：2026-09-22
> 时间范围：2026-2028
> 修订：本版由 **Claude（Opus 5）** 依据 2026-09-22 评审意见改写。v0.1 原稿见 [_original-v0.1/VISION.md](_original-v0.1/VISION.md)，逐条改动见 [../REVIEW-CHANGES.md](../REVIEW-CHANGES.md)。改动以 `〔C·改〕`、`〔C·新〕`、`〔C·删〕` 标记。

## 〔C·改〕1. 愿景声明

建设一个开放、可替换、可自托管的 AI Native SDLC Control Plane，使**小团队**能够在明确意图、充分上下文、受控权限和可验证证据的基础上，让 AI Agent 持续参与软件交付，并且**让审查这件事随 Agent 产出量一起扩展**。

长期目标不是让 AI 生成更多代码，而是让 AI 参与的软件变更具备与成熟软件工程同等级别的：

- 目标清晰度；
- 过程可控性；
- 结果可验证性；
- 决策可问责性；
- 全程可追溯性；
- 故障可恢复性。

〔C·新〕以上六项是**结果**。第一阶段被验证的**手段**只有一个：把审查一次 AI 变更所需的时间显著降下来。如果这一项不成立，其余六项在小团队里不会有人为之付出成本。

## 2. 问题定义

Coding Agent 正在显著降低代码生成成本，但软件交付仍存在系统性缺口。

### 〔C·新〕2.0 审查带宽缺口（首要缺口）

编码环节快了十几倍，而需求澄清、代码审查和上线验证仍按人的速度运行，端到端周期几乎没有变化。在小团队里，这个缺口表现为两种都很糟的结果：

1. **审查成为瓶颈**：变更堆积在 PR 队列里，Agent 的产能无法转化为交付速度；
2. **审查退化为橡皮章**：为了不堵塞流水线，审查者在没有真正理解变更的情况下点通过，团队获得形式完备、实质为零的质量保证。

第二种比第一种更危险，因为它制造虚假安全感。本项目存在的首要理由是消除这个缺口，其余五个缺口是它的组成部分。

### 2.1 意图缺口

Agent 经常接收到模糊、局部、缺乏约束的任务描述，导致它能够快速产出代码，却无法证明产出真正满足业务目标。〔C·新〕在团队场景下，这个缺口额外产生一个后果：**审查者无从判断"对不对"，因为没人写下过"什么算对"。**

### 2.2 上下文缺口

Agent 缺少稳定的业务规则、架构决策、历史缺陷、代码关系和组织规范。当前上下文通常依赖临时提示词，难以复现、审计和复用。〔C·新〕审查者也因此无法回答一个基本问题：它当时到底看见了什么，有没有看见关键的那个文件。

### 2.3 控制缺口

Agent 被授予的文件、命令、网络、凭证和环境权限缺少统一策略。工具调用能力增长快于组织对权限、风险和爆炸半径的治理能力。〔C·新〕团队共享仓库使这个缺口的后果放大：出问题的是别人的 Agent，承担后果的是整个团队。

### 2.4 评估缺口

"Agent 声称已经完成"与"结果可以交付"之间缺少统一评估体系。代码生成加速后，瓶颈向验证、审查和生产集成转移。

〔C·新〕一个必须单独点出的子问题：**Agent 经常同时编写实现和证明它正确的测试。** 这在形式上完全符合"有测试覆盖"，实质上是自己给自己判卷。作者本人凭直觉可能察觉，接手审查的同事没有这个直觉。识别并标注"本次新增的测试"，是本项目评估层最便宜也最高价值的单点能力。

### 2.5 证据缺口

现有平台很难完整回答一次 AI 变更为什么发生、使用了什么上下文、执行了哪些操作、通过了哪些评估、由谁批准以及如何回滚。

〔C·新〕需要诚实界定增量。今天的 PR + CI 日志已经能提供变更内容、测试结果和扫描结果。**现有工具真正缺失的只有两项**：

1. Agent 本次实际使用的上下文及其版本（Context Manifest）；
2. 验收标准与证明它的评估项之间的映射，以及其中哪些证明是本次新造的。

第一阶段的证据能力优先做这两项，其余部分是对 CI 既有输出的重新组织。

## 3. 产品角色

Control Plane 是覆盖在现有研发工具之上的控制层，而不是替代层。

```text
                         AI Native SDLC Control Plane
┌─────────────────────────────────────────────────────────────────┐
│ Intent │ Context │ Work Graph │ Policy │ Evaluation │ Evidence │
└─────────────────────────────────────────────────────────────────┘
       │          │             │          │             │
       ▼          ▼             ▼          ▼             ▼
  Issue/Spec   Code/Docs    Coding Agent   CI/Test    Git/Release
```

它负责决定：

- 为什么做；
- 要做成什么样；
- 谁或哪个 Agent 可以做；
- 可以使用哪些上下文和工具；
- 什么条件下可以继续；
- 如何证明结果正确；
- 谁能批准进入下一阶段。

现有 Agent、Git 平台、Issue Tracker 和 CI/CD 负责执行具体操作。

### 〔C·新〕3.1 每一层的读者

产品定义的每一项能力都必须指明它的读者，否则会做出无人阅读的产物。

| 层 | 主要读者 | 读它是为了回答 |
| --- | --- | --- |
| Intent | 审查者、未来的自己 | 这次变更想达成什么，什么算达成 |
| Context Manifest | 审查者、调试的人 | 它当时看见了什么，漏看了什么 |
| Policy Decision | 审查者、事故复盘 | 它被允许做什么，哪些被拦下了 |
| Evaluation | 审查者 | 哪条验收标准被什么证明了，证明是谁造的 |
| Evidence | **审查者（唯一主要读者）** | 我能不能在 8 分钟内安全地接受它 |
| Metrics | 团队推动者 | 审查负载在谁身上，哪类任务返工最多 |

〔C·新〕第一阶段没有"审计员"这个读者。为审计员设计的能力（签名、跨组织传递、合规报表）全部推迟。

## 4. 北极星

### 4.1 北极星问题

对任何进入主分支或生产环境的 AI 变更，系统都应能够回答：

1. 它关联哪个 Intent？
2. Intent 的目标、约束和验收标准是什么？
3. Agent 使用了哪些上下文及其版本？
4. Agent 具有什么临时权限？
5. Agent、工具和人分别执行了什么？
6. 哪些确定性和概率性评估通过？〔C·新〕其中哪些证明是本次新造的？
7. 存在哪些残余风险？
8. 谁基于哪些证据批准？
9. 如何回滚或补偿？

### 〔C·改〕4.2 北极星指标

v0.1 使用的公式（可信意图数 ÷ 时间×成本×风险）无法计算，已删除。第一阶段用三个可测量的数替代：

| 指标 | 定义 | 第一阶段目标 |
| --- | --- | --- |
| 审查人时 | 每个被接受变更从进入审查到批准的人工投入 | 相对基线下降 ≥ 30% |
| 证据展开率 | 非作者审批者在点批准前展开过证据的比例 | ≥ 70% |
| 首次评估通过率 | Run 第一次跑完评估即全部必需门禁通过的比例 | 建立基线并持续上升 |

**证据展开率是本项目的核心否证指标。** 它低于 50% 意味着产品正在生产橡皮章审批，核心价值假设不成立，必须转向。这个数由产品自己采集，无需外部调研。

第一阶段不把代码行数、Prompt 数量、Agent 调用次数、AI 使用率或 GitHub Star 作为成功指标。

## 5. 方法论框架

### 5.1 生命周期主线

```text
Intent → Plan → Execute → Evaluate → Review → Approve → Release → Learn
```

〔C·改〕相比 v0.1 显式插入 `Review`。审查是一个有成本、有承载者、有排队、会退化的独立环节，把它折叠进 Approve 会让它在设计中消失。

### 5.2 三个横切控制面

| 控制面 | 核心问题 |
| --- | --- |
| Context | Agent 知道什么，信息是否正确、充分、及时？ |
| Governance | Agent 被允许做什么，何时必须停止或请求人工？ |
| Evidence | 如何**以最低的阅读成本**证明结果满足意图并符合策略？ |

〔C·改〕Evidence 控制面的成功条件不是"证据完整"，而是"证据能被快速读懂"。完整但无人阅读的证据等于没有证据。

### 5.3 最终责任

AI 可以分析、生成、调用工具和执行任务，但不能成为责任主体。需要判断、承担风险或改变信任边界的决策必须归属到具名的人类角色。

〔C·新〕具名要有意义，身份就必须不可自证。第一阶段的审批身份来自外部身份源（GitHub 账号），不接受本地配置文件里的一个字符串。

## 6. 核心设计原则

### 〔C·新〕6.0 Review Bandwidth before Governance

一切治理形式的价值，先用"是否降低审查成本"来检验。会增加审查负担的治理能力，推迟到它能同时降低负担时再做。

### 6.1 Reuse before Build

优先采用开放标准，集成成熟项目，扩展已有能力，只自研差异化领域模型。

### 6.2 Evidence before Trust

不接受"任务已完成"的声明，只接受可复现的测试、扫描、场景评估和审批证据。〔C·新〕并且不接受由被评估者本次新造、且未被标注的证明。

### 6.3 Policy before Autonomy

先建立权限、门禁、预算、升级人工和回滚规则，再逐步提高自治等级。

### 6.4 Repository before Platform

第一阶段让 Intent、Specification、Policy 和 Evaluation Definition 尽可能进入 Git，避免过早建设封闭平台数据库。

### 〔C·新〕6.5 Attach before Replace

对团队已在使用的系统（Issue Tracker、CI、Git 平台），只做附着与同步，不做替代。**任何会制造第二个权威数据源的设计都被视为缺陷。** 团队不会为一个未经验证的工具迁移他们的需求管理。

### 〔C·新〕6.6 Enforce at the Boundary

策略只在能够真正阻止的边界上声明为强制。凡不在该边界上的规则，明确标注为**检测性**而非**预防性**，并在证据里如实呈现。不允许出现"写在文档里、实际拦不住"的策略。

### 〔C·改〕6.7 Self-hosted before SaaS

核心能力必须可完全自托管、可离线运行、可使用本地模型。这是**部署原则**，不是架构限制：团队共享服务从第一阶段起就存在，只是它跑在团队自己的机器上。

〔C·改〕v0.1 的 "Local before Cloud" 被误读为"一切都在个人笔记本上"，与团队定位不兼容，故重写。

### 6.8 Protocol before Vendor

核心模型不绑定特定模型、Agent、Git 平台、CI/CD 或云厂商。

### 〔C·改〕6.9 Graduated Autonomy over Blanket Review

进入主分支的变更按风险分级决定审批强度。**要求全部变更都由人审批，在团队场景下等价于取消审批**——它必然退化为橡皮章。低风险变更自动合并不是放松管控，而是把稀缺的人类注意力集中到高风险变更上的手段。

自治等级必须按任务、系统、环境、Agent 能力和风险动态计算，不能以组织级开关统一开启。

### 6.10 Observable Autonomy

任何自动决策必须产生可查询的输入、策略、结果和证据。不可观测的自治不进入生产链路。

### 6.11 Deterministic Core

状态转换、策略门禁、证据打包、ID 生成和审批判断由确定性程序执行，不交给模型自行决定。

## 〔C·改〕7. 目标用户

v0.1 的四阶段用户演进（个人 → 小团队 → 平台工程 → 企业治理）已删除：它把四类差异极大的产品写成了一条路线，并且让第一阶段的核心产物（证据、审批）落在了唯一没有读者的场景上。

### 7.1 第一阶段：小团队（3–8 人）

- 已在使用一个或多个 Coding Agent；
- 维护真实生产项目，自己开发也自己运维；
- 审查带宽已经成为或即将成为瓶颈；
- 无专职平台工程师，无强制合规要求；
- 能接受 CLI + Git + GitHub 的工作方式。

**两个 persona 同时存在，且第二个更重要：**

| Persona | 关心 |
| --- | --- |
| 作者 | 让 Agent 在明确要求和受限权限下干活，少返工 |
| **审查者** | 快速、安全地决定是否接受同事的 Agent 产出的变更 |

### 7.2 第二阶段：自托管的团队平台

多团队、多仓库、共享评估资产、组织级指标、外部身份联邦、可选的合规导出。

### 7.3 采用单位与安装单位

个人是**安装单位**（一个人装上就能用、就能产生价值），团队是**生效单位**（价值在第二个人开始审查时才完全兑现）。产品必须同时满足这两点，见 [../README.md](../README.md) 的采用路径。

## 8. 自治演进

| 等级 | 描述 | 第一阶段 |
| --- | --- | --- |
| L0 | AI 只提供建议 | 支持 |
| L1 | AI 生成制品，不执行环境操作 | 支持 |
| L2 | AI 在隔离环境执行，人工决定是否采用 | 支持 |
| L3 | AI 自动提交分支或 PR，人工审查后合并 | **默认模式，MVP 目标** |
| L4 | 低风险变更在证据充分时自动合并 | 〔C·改〕月 5 起在团队内试验 |
| L5 | 在受限策略内自动发布和运营 | 长期研究 |

〔C·改〕v0.1 同时把 L2 写成"默认模式"、L3 写成"MVP 目标"，与 MVP 旅程以创建 PR 结束互相矛盾，现统一为 L3。L4 从"后续阶段"提前到第一阶段末的受控试验，理由见 6.9。

## 〔C·改〕9. 两年目标

到 2028-09，项目希望实现：

1. 一套可被讨论和引用的 AI Native SDLC 方法论，并以真实团队数据支撑；
2. 开放的 Intent、Context Manifest、Evaluation 和 Evidence Schema，含版本迁移规范；
3. 可运行的自托管开源 Control Plane，支持个人安装与团队部署；
4. 至少 5 个团队在真实项目中持续使用，并公开审查人时与返工率的前后对比；
5. GitHub 与主流 Coding Agent 的稳定 Adapter，以及一个外部贡献的 Adapter；
6. 多个真实项目的实践案例与公开复盘（含失败案例）。

〔C·删〕删除"形成 GitHub/GitLab/Jira/CI/CD 生态"与"建立专业影响力"两项：生态与影响力是采用量的**结果**，不是可以直接规划的目标；把它们写成目标会诱导项目在没有用户时先去做标准化和布道。

## 10. 长期不变的边界

项目原则上不建设：

- 基础大模型；
- 封闭的专属 Coding Agent；
- Git 托管平台替代品；
- 通用 CI/CD 替代品；
- 〔C·新〕Issue Tracker 替代品；
- 自有 Agent 通信协议；
- 必须连接公有云才能工作的核心能力。

〔C·新〕第一阶段额外不建设（可在后续阶段重新评估）：

- Web 审批后台（v1 的审查界面就是 GitHub PR）；
- RBAC 与多租户；
- 多仓库跨仓变更；
- 合规报表与证据签名。

项目的长期价值应集中在：

- Intent Graph；
- Context Supply Chain；
- Risk-adjusted Autonomy；
- Evaluation Contract；
- Evidence Graph；
- Intent-to-Production Traceability。

〔C·删〕"AI Native SDLC Metrics" 从差异化核心中移除：指标定义本身没有护城河，它是上述能力的副产品。指标集本身仍然保留在 [OPEN_SOURCE_LANDSCAPE.md](OPEN_SOURCE_LANDSCAPE.md) 中作为度量口径。
