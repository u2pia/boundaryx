# AI Native SDLC Control Plane 愿景

> 状态：Draft v0.1  
> 日期：2026-09-22  
> 时间范围：2026-2028

## 1. 愿景声明

建设一个开放、可替换、可私有化的 AI Native SDLC Control Plane，使个人和组织能够在明确意图、充分上下文、受控权限和可验证证据的基础上，让 AI Agent 持续参与软件交付。

长期目标不是让 AI 生成更多代码，而是让 AI 参与的软件变更具备与成熟软件工程同等级别的：

- 目标清晰度；
- 过程可控性；
- 结果可验证性；
- 决策可问责性；
- 全程可追溯性；
- 故障可恢复性。

## 2. 问题定义

Coding Agent 正在显著降低代码生成成本，但软件交付仍存在五个系统性缺口。

### 2.1 意图缺口

Agent 经常接收到模糊、局部、缺乏约束的任务描述，导致它能够快速产出代码，却无法证明产出真正满足业务目标。

### 2.2 上下文缺口

Agent 缺少稳定的业务规则、架构决策、历史缺陷、代码关系和组织规范。当前上下文通常依赖临时提示词，难以复现、审计和复用。

### 2.3 控制缺口

Agent 被授予的文件、命令、网络、凭证和环境权限缺少统一策略。工具调用能力增长快于组织对权限、风险和爆炸半径的治理能力。

### 2.4 评估缺口

“Agent 声称已经完成”与“结果可以交付”之间缺少统一评估体系。代码生成加速后，瓶颈向验证、审查和生产集成转移。

### 2.5 证据缺口

现有平台很难完整回答一次 AI 变更为什么发生、使用了什么上下文、执行了哪些操作、通过了哪些评估、由谁批准以及如何回滚。

## 3. 产品角色

Control Plane 是覆盖在现有研发工具之上的控制层，而不是替代层。

```text
                         AI Native SDLC Control Plane
┌─────────────────────────────────────────────────────────────────┐
│ Intent │ Context │ Work Graph │ Policy │ Evaluation │ Evidence │
└─────────────────────────────────────────────────────────────────┘
       │          │             │          │             │
       ▼          ▼             ▼          ▼             ▼
  Issue/Spec   Code/Docs    Coding Agent   CI/Test    Git/Release
```

它负责决定：

- 为什么做；
- 要做成什么样；
- 谁或哪个 Agent 可以做；
- 可以使用哪些上下文和工具；
- 什么条件下可以继续；
- 如何证明结果正确；
- 谁能批准进入下一阶段。

现有 Agent、Git 平台和 CI/CD 负责执行具体操作。

## 4. 北极星

### 4.1 北极星问题

对任何进入主分支或生产环境的 AI 变更，系统都应能够回答：

1. 它关联哪个 Intent？
2. Intent 的目标、约束和验收标准是什么？
3. Agent 使用了哪些上下文及其版本？
4. Agent 具有什么临时权限？
5. Agent、工具和人分别执行了什么？
6. 哪些确定性和概率性评估通过？
7. 存在哪些残余风险？
8. 谁基于哪些证据批准？
9. 如何回滚或补偿？

### 4.2 北极星指标

```text
可信交付的业务意图数量
────────────────────
时间 × 成本 × 风险
```

第一阶段不把代码行数、Prompt 数量、Agent 调用次数或 AI 使用率作为成功指标。

## 5. 方法论框架

### 5.1 生命周期主线

```text
Intent → Plan → Execute → Evaluate → Approve → Release → Learn
```

### 5.2 三个横切控制面

| 控制面 | 核心问题 |
|---|---|
| Context | Agent 知道什么，信息是否正确、充分、及时？ |
| Governance | Agent 被允许做什么，何时必须停止或请求人工？ |
| Evidence | 如何证明结果满足意图并符合策略？ |

### 5.3 最终责任

AI 可以分析、生成、调用工具和执行任务，但不能成为责任主体。需要判断、承担风险或改变信任边界的决策必须归属到具名的人类角色。

## 6. 核心设计原则

### 6.1 Reuse before Build

优先采用开放标准，集成成熟项目，扩展已有能力，只自研差异化领域模型。

### 6.2 Evidence before Trust

不接受“任务已完成”的声明，只接受可复现的测试、扫描、场景评估和审批证据。

### 6.3 Policy before Autonomy

先建立权限、门禁、预算、升级人工和回滚规则，再逐步提高自治等级。

### 6.4 Repository before Platform

第一阶段让 Intent、Specification、Policy 和 Evaluation Definition 尽可能进入 Git，避免过早建设封闭平台数据库。

### 6.5 Local before Cloud

第一阶段默认本地优先，支持离线、私有仓库、本地模型和自托管 Agent。

### 6.6 Protocol before Vendor

核心模型不绑定特定模型、Agent、Git 平台、CI/CD 或云厂商。

### 6.7 Human Accountability by Default

第一阶段所有进入主分支的变更必须由人审批。自治能力按风险逐步开放，而不是一次性授予。

### 6.8 Observable Autonomy

任何自动决策必须产生可查询的输入、策略、结果和证据。不可观测的自治不进入生产链路。

## 7. 目标用户演进

### 阶段一：个人开发者

希望使用 Coding Agent，但不愿牺牲需求质量、工程纪律和代码控制权。

### 阶段二：小型研发团队

需要共享 Intent、评估规则、Agent 配置、审批流程和交付证据。

### 阶段三：平台工程团队

需要统一接入多个 Agent、模型、代码仓库、CI/CD 和组织政策。

### 阶段四：企业治理与研发管理

需要私有化、多租户、身份联邦、审计、合规、成本和组织级指标。

## 8. 自治演进

| 等级 | 描述 | 第一阶段支持 |
|---|---|---|
| L0 | AI 只提供建议 | 支持 |
| L1 | AI 生成制品，不执行环境操作 | 支持 |
| L2 | AI 在隔离环境执行，人工决定是否采用 | 默认模式 |
| L3 | AI 自动提交分支或 PR，人工合并 | MVP 目标 |
| L4 | 低风险变更自动合并 | 后续阶段 |
| L5 | 在受限策略内自动发布和运营 | 长期研究 |

自治等级必须按任务、系统、环境、Agent 能力和风险动态计算，不能以组织级开关统一开启。

## 9. 两年目标

到 2028-09，项目希望实现：

1. 发布一套可被讨论和引用的 AI Native SDLC 方法论；
2. 建立开放的 Intent、Agent Runtime、Evaluation 和 Evidence Schema；
3. 提供可运行的本地优先开源 Control Plane；
4. 支持个人、团队和完全私有化部署；
5. 形成 GitHub、GitLab、Jira、CI/CD 和 Agent Adapter 生态；
6. 形成多个真实项目的实践案例和公开复盘；
7. 建立 AI 软件工程评估、治理和可追溯性的专业影响力。

## 10. 长期不变的边界

项目原则上不建设：

- 基础大模型；
- 封闭的专属 Coding Agent；
- Git 托管平台替代品；
- 通用 CI/CD 替代品；
- 自有 Agent 通信协议；
- 必须连接公有云才能工作的核心能力。

项目的长期价值应集中在：

- Intent Graph；
- Context Supply Chain；
- Risk-adjusted Autonomy；
- Evaluation Contract；
- Evidence Graph；
- Intent-to-Production Traceability；
- AI Native SDLC Metrics。
