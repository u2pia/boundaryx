# BoundaryX 团队上手说明（试用版）

这份说明写给参加试用的同事。读完就能走通一遍：写需求 → AI 改代码 → 有人审查 → 合并。

## 这是什么

你用中文写下要改什么、怎样才算改好，找一位同事批准。然后 AI 在单独的分支上改代码，平台自动跑测试、整理证据。最后由另一位同事看过证据后批准合并。

每一步是谁、在什么时候做的，平台都会记下来，事后可以查。

## 登录

- 地址：`http://<服务所在机器的局域网 IP>:8787`，由管理员告诉你。
- 账号：由管理员创建。目前只有管理员能改密码，要改密码请找管理员。
- 侧栏顶部的项目切换器选 **试用项目**。「默认项目」里是演示数据，可以随便看，不要在里面干活。

## 角色：谁能做什么

| 角色 | 能做的事 |
| --- | --- |
| 开发（developer） | 写需求、启动 AI、查看结果 |
| 审查（reviewer） | 在上面的基础上，还能批准别人的需求和代码 |
| 维护（maintainer） | 在上面的基础上，还能分配审查人 |
| 负责人（owner） | 在上面的基础上，还能管理成员、配置项目，在必要时带理由「推翻」门禁 |

一条规则贯穿始终：**自己写的东西不能自己批准**。需求要换人批，代码也要换人批。

## 走一遍流程

### 1. 写需求（Intents 页）

点「套用模版」，把所有 `<...>` 占位符都替换成真实内容。需要填三样东西：

- **目标**：要改什么。
- **约束**：不能碰什么。例如「不改数据库结构」。
- **验收标准**：每行一条，写成能检查的句子，带上具体数值或错误码。
  - 好的写法：`导入 1000 行 CSV 在 2 秒内完成`
  - 不好的写法：`性能更好`

标准前面可以加标记：

- 什么都不写：默认是「关键、由测试证明」。
- `[人工]`：由人判断。例如 `[人工] 产品负责人确认文案无歧义`。
- `[参考]`：参考项，不影响合并。

风险等级按实际情况选：

- **低**：提交后自动批准。
- **中、高**：要一位同事批准。高风险还必须至少有一条关键的 `[人工]` 标准。

### 2. 批准需求（Intents 页，由另一位同事操作）

读一遍需求，点「批准 Intent」。

### 3. 让 AI 动手（Agent Runs 页）

选择已批准的需求，启动 Run。AI 默认最多做 10 分钟：

- 时间到时，已有的改动照样交出来，并标为「部分变更」。
- 失败的 Run 会显示原因，可以改需求后重来。

### 4. 审查（评审队列）

审查人打开提案，**先展开证据**（改了哪些文件、测试结果、每条验收标准的状态），再选择：

- **批准**：批准意见里要写明理由。
  - 如果有 `[人工]` 标准，要逐条点名，例如：`AC-2：已和产品确认文案`。
  - 如果是「部分变更」，要写明为什么接受。
- **请求修改**：写下问题，重新让 AI 改。
- **拒绝**：写明理由，提案随即关闭，不能再继续。

### 5. 合并

批准后即可合并。仓库接的是 GitHub 时，平台会开一个 PR。

## 常见卡点

| 看到的提示 | 意思 | 怎么办 |
| --- | --- | --- |
| **仅自带测试** | 这条标准只被 AI 自己写的测试证明过，不能算数 | 请管理员在项目配置里声明哪些是「已有测试」；或者人工确认后，由负责人带理由推翻 |
| **评测未隔离** | 模型评测的分数是 AI 自己环境里跑出来的 | 由负责人看过结果后带理由推翻 |
| **无可映射检查** | 这条标准没有对应的测试可以证明 | 把标准改写得更具体，或者改成 `[人工]` |
| **部分变更** | AI 到时间了，改动可能不完整 | 看情况批准（写明原因）或请求修改 |
| 不能批准自己的提案 | 平台设计如此 | 找另一位同事 |

## 试用期间请注意

- 只用这几页：**Intents、Agent Runs、评审队列、项目、团队**。其他页面目前多是演示数据。
- 服务装在一台机器上。那台机器关机或休眠，大家就都用不了。
- 只在公司内网里使用，不要把地址发到外面。
- 遇到看不懂的提示，截图发给管理员，这正是试用要收集的反馈。

## 附：管理员准备清单（Owner）

1. 服务机器设为不休眠，并固定局域网 IP。启动服务时加上 `CONTROL_PLANE_HOST=0.0.0.0`，否则服务只接受本机访问，同事连不上。这时是明文 HTTP，只在可信内网使用。
2. 在「团队」页为每个人创建账号。
3. 在「项目」页新建 **试用项目**，接入要试用的仓库（本地 Git 或 GitHub），并把成员加进项目、分好角色。审查人至少两位。
4. 在仓库里提交 `.aperture/project.json`，写明测试命令。如果有现成测试，用 `testPaths` 声明测试目录，这样能避开「仅自带测试」的卡点。格式见 `workbench/README.md` 的「Project Manifest」一节。
5. 在「集成」页确认 LLM Provider 可用，先自己跑通一条低风险需求。
6. 每天备份一次数据目录 `workbench/.aperture-live/`，备份前先停服务，或者用 `sqlite3 .backup` 备份数据库。
